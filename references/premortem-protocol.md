# Premortem Protocol — общий протокол для всех агентов

> **Статус**: общий референс для всех агентов крю.
> **Использование**: любой агент, у которого включена секция "Premortem capability" или "Premortem awareness", должен опираться на этот документ при обработке premortem-запросов.
> **Связано**: `02-Areas/Личное/Стратегия/Premortem - техника предразбора провала.md` (концептуальная статья), `02-Areas/Личное/Стратегия/Premortem/_Index.md` (индекс по всем целям).

---

## 1. Что такое premortem

Premortem (предразбор провала) — техника Гэри Кляйна / Даниэля Канемана. Перед стартом любой важной цели команда (или сам пользователь) представляет, что цель провалилась через N месяцев, и в этой воображаемой реальности раскладывает механику провала: что именно сломалось, какие сигналы были видны, какие допущения оказались неверными, какие контрмеры можно было применить заранее.

Это не пессимизм. Это **обязательный фильтр перед запуском цели** в Канбане Сергея.

Ключевая мысль: люди гораздо точнее предсказывают будущее в режиме объяснения уже случившегося (prospective hindsight), чем в режиме прогноза. Premortem использует этот когнитивный паттерн как инструмент.

## 2. Когда применять

### Триггеры пользователя

- "premortem"
- "премортем"
- "premortem this"
- "премортем цели X"
- "премортем перед стартом"
- "разберём что может пойти не так"
- "что может пойти не так"
- "разбери провал"
- "if we fail"
- "представь, что мы провалились"
- "сценарий провала"

### Автоматические триггеры (агент должен предложить сам)

- Цель переводится из "В планах" 🟡 в "В работе" 🟢 в Канбане — **обязательный** premortem перед переводом (см. `goals-kanban`).
- Пользователь добавляет новую цель в список (см. `goals-list`).
- Пользователь говорит о большой цели, но без плана.
- В дневниках/отчётах виден срыв одного и того же типа второй раз подряд.
- Финансовое решение с горизонтом > 3 месяца (см. `finance-analyst`).
- Медицинский протокол длительный или с риском срыва (см. `home-doctor`, `health-therapist`).

## 6. Алгоритм работы агента

### A. Запуск premortem (триггер пользователя)

1. **Определи цель** — из контекста сообщения, из открытой заметки, из Канбана, или спроси у пользователя.
2. **Проверь существование файла**: `02-Areas/Личное/Стратегия/Premortem/<категория>/<название цели>.md`.
   - Существует и пустой каркас → перейти к шагу 4 (развернуть секции).
   - Существует и развёрнутый → перейти к шагу 5 (новая ревизия).
   - Не существует → перейти к шагу 3.
3. **Создание нового premortem-каркаса**:
   - Определи категорию (одна из 11 папок).
   - Создай файл по шаблону выше.
   - Заполни frontmatter полностью.
   - Перейди к шагу 4.
4. **Разверни 7 секций**:
   1. Сценарий провала — нарратив "почему мы здесь оказались".
   2. Топ-3 точки отказа — отсортированные по вероятности.
   3. Самый критичный сценарий — тот, что бьёт сильнее всего.
   4. Самое рискованное скрытое допущение — что считалось данностью.
   5. Ранние сигналы — обязательно как `- [ ]` чекбоксы, наблюдаемые в дневниках/дашбордах.
   6. Контрмеры — обязательно как `- [ ]` чекбоксы, привязаны к точкам отказа.
   7. Пересобранный план — конкретные шаги.
5. **Добавь запись в Журнал ревизий**: дата + событие "Развёрнут premortem (агент: <имя_агента>)".
6. **Предложи отслеживание сигналов**:
   - Преобразуй "Ранние сигналы" в чекбоксы.
   - Предложи добавить ключевые метрики в дашборд (через `dashboard-updater` или `health-dashboard-updater`).
   - Предложи проверку в `daily-diary` раз в неделю.
7. **Связь обратно**:
   - В выводе укажи путь к файлу.
   - Если premortem выявил серьёзные проблемы — `### Suggested next agent: coach` (для обсуждения).

### B. Обновление существующего premortem

1. Прочитай текущий файл целиком.
2. Сохрани историю в Журнале ревизий — никогда не перетирай старые секции, делай diff.
3. Если статус цели изменился (`В планах` → `В работе`, `В работе` → `Отложено`) — обнови frontmatter.
4. Добавь запись в Журнал ревизий с описанием изменений.

### C. Постфактум-проверка (life-analytics)

Раз в период анализа `life-analytics` проверяет:
- Сработали ли предсказанные ранние сигналы?
- Какие контрмеры были выполнены, какие нет?
- Какие точки отказа реализовались?
- Нужно ли пересобрать план?

Результат — записать в Журнал ревизий и при необходимости предложить новую ревизию через `coach`.

## 7. Mode-режим "premortem"

Когда агент работает в premortem-режиме, действуют особые правила:

1. **Не ищи причины, почему план сработает.** Это анти-оптимистичный режим. Все аргументы "у нас получится" игнорируй или вытесняй в раздел "Допущения".
2. **Раскладывай конкретную механику провала.** Не "может не получиться", а "к 3-му месяцу пользователь начнёт пропускать тренировки по понедельникам, потому что..."
3. **Используй prospective hindsight.** Пиши в прошедшем времени: "цель провалилась, потому что...".
4. **Привязывай каждый риск к наблюдаемому сигналу.** Если ты не можешь придумать, как этот риск будет виден в дневнике/дашборде/Канбане — этот риск бесполезен, замени.
5. **Контрмеры должны быть конкретны и проверяемы.** "Лучше планировать" — плохо. "Заносить в дневник в 22:00 план на завтра" — хорошо.
6. **Не успокаивай пользователя.** Premortem — это не терапия, это аудит планов.

---

## 8. Что делать с ранними сигналами

После генерации premortem список ранних сигналов должен жить дальше:

1. **Чекбоксы в файле** — основной носитель.
2. **Опционально**: создать запрос к `dashboard-updater` для добавления метрики в дашборд.
3. **Опционально**: создать запрос к `daily-diary` — добавить "проверку сигналов premortem" в еженедельную ревизию.
4. **Опционально**: для финансовых сигналов — связать с `expense-diary` (лимиты, тревожные категории).
5. **Опционально**: для здоровья — связать с `home-doctor` или `health-therapist` (метрики анализов, давление, КБЖУ).

## 9. Связь с другими агентами

| Агент | Роль в premortem |
|---|---|
| `coach` | Универсальная точка входа для premortem любой цели. Видит весь Канбан. |
| `goals-kanban` | **Обязательный** premortem при переводе цели 🟡 → 🟢. |
| `goals-list` | Premortem при добавлении новой цели. |
| `finance-analyst` | Финансовые цели (доход, бюджет, инвестиции). |
| `home-doctor` / `health-therapist` | Здоровье, протоколы лечения, режимы препаратов. |
| `cbt-therapist` | Психология, привычки, протоколы восстановления. |
| `food-diary` | Диета, КБЖУ, срывы питания. |
| `expense-diary` | Бюджетная дисциплина, лимиты по категориям. |
| `daily-diary` | Мини-premortem на "Цели на завтра", ретроспектива провалов дня. |
| `therapy-diary` | Premortem психотерапевтических домашних заданий. |
| `scribe` | Создание новых premortem-заметок по запросу. |
| `seeker` | Поиск существующих premortem, связывание с целями. |
| `architect` | Поддержка структуры папки Premortem, шаблоны, новые категории. |
| `librarian` | Health-чек premortem-папки, актуальность дат, статусы. |
| `life-analytics` | Постфактум-проверка: сработали ли сценарии. |

Остальные агенты (`postman`, `transcriber`, `sorter`, `connector`, `dashboard-updater`, `health-dashboard-updater`, `folder-icon-updater`, парсеры) работают в режиме **awareness** — упоминают возможность запустить premortem через релевантный домен-агент, если в работе встречается решение с заметным риском.

## 10. Чек-лист качества premortem

Прежде чем отдать пользователю результат, агент проверяет:

- [ ] Сценарий провала написан в прошедшем времени и конкретен (не абстрактен).
- [ ] Топ-3 точки отказа упорядочены по вероятности.
- [ ] Самый критичный сценарий отличается от топ-1 точки отказа.
- [ ] Скрытое допущение названо явно и привязано к конкретному решению.
- [ ] Каждый ранний сигнал наблюдаем в дневнике/дашборде/Канбане.
- [ ] Каждая контрмера привязана к точке отказа или скрытому допущению.
- [ ] Пересобранный план содержит конкретные действия и временные рамки.
- [ ] В Журнале ревизий есть свежая запись.
